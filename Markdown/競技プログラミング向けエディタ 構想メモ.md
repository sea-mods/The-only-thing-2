# 競技プログラミング向けエディタ 構想メモ

## 1. 基本コンセプト

このエディタの目的は、単にコードを書くことではなく、

> **問題を読んでから、実装・テスト・修正・提出までの操作をできるだけ短くすること**

にある。

特に、

- C++
- AtCoderなどの一般的な競技プログラミング
- ヒューリスティックコンテスト

を主な対象として考える。

既存のVS Codeなどとの差別化として、

> **Code → Test → Diagnose → Modify**

という競プロ特有の反復作業を高速化することを重視する。

---

# 2. エディタ全体の構成

基本画面は、以下の4要素を中心に構成する。

- Problem
- Code
- Test
- Library

イメージ：

```text
┌─────────────────────────────────────────────┐
│ Problem / Contest                           │
├──────────────┬──────────────────────────────┤
│              │                              │
│ Testcases    │            Editor            │
│              │                              │
│ sample 1 ✓   │  #include <bits/stdc++.h>    │
│ sample 2 ✗   │                              │
│ custom   ✓   │  int main() {                │
│              │      ...                     │
│              │  }                           │
├──────────────┴──────────────────────────────┤
│ Compile / Output / Diff / Execution Time    │
└─────────────────────────────────────────────┘
```

ライブラリマネージャーについては、常時表示するのではなく、

> **必要に応じて別ウインドウとして開く**

方式を中心に考える。

これにより、通常のコーディング中は画面をシンプルに保てる。

---

# 3. テストケース管理

競プロではテストが非常に重要なので、テストケースをエディタの中心機能として扱う。

## サンプルテスト

ショートカット1つで、

```text
Sample 1   AC   3 ms
Sample 2   AC   2 ms
Sample 3   WA   2 ms
```

のように全サンプルを実行する。

WAの場合は、

```text
Expected:
10

Actual:
11

Diff:
- 10
+ 11
```

のように差分を表示する。

---

## Custom Test

任意入力を保存できるようにする。

```text
Samples
  sample 1
  sample 2
  sample 3

Custom
  n_equals_1
  max_N
  duplicate
  bug_case_01
```

バグを発見した入力を保存しておけば、その後コードを変更した際にもまとめて再テストできる。

---

# 4. 実行履歴

コードの変更とテスト結果を記録する。

例：

```text

Sample 1 AC
Sample 2 AC
Sample 3 WA

Run #19
23:15:21

Sample 1 AC
Sample 2 AC
Sample 3 AC
```

さらに、

```text
23:14
Sample 3 WA

line 47
<= → <

23:15
Sample 3 AC
```

のように、

- コード変更
- テスト結果

を関連付ける。

競技中に、

> 「さっき動いていたコードに戻したい」

という状況にも対応できるようにする。

Gitほど大規模ではない、

> **競技中専用の軽量なコード履歴**

として扱う。

# 5. Scratchpad / 思考メモ

問題ごとに簡単なメモ領域を持つ。

例：

```text
Idea

・二分探索
・単調性あり
・overflow注意

Complexity
O(N log N)
```

また、

```text
TODO

☐ N = 1
☐ overflow
☐ duplicate
☐ 0-index / 1-index
```

のようなチェックリストも作成できるようにする。

# 6. 競プロ用コード補完

一般的な単語補完だけでなく、競技プログラミング向けのコード補完を用意する。

例えば、

```text
bfs
```

から、

```cpp
queue<int> q;
vector<int> dist(n, -1);

dist[s] = 0;
q.push(s);

while (!q.empty()) {
    int v = q.front();
    q.pop();

    for (int nv : g[v]) {
        if (dist[nv] != -1) continue;

        dist[nv] = dist[v] + 1;
        q.push(nv);
    }
}
```

のようなテンプレートを挿入する。

候補例：

```text
BFS
BFS Grid
0-1 BFS
Dijkstra
Binary Search
Union Find
Fenwick Tree
Segment Tree
```

# 7. SnippetとLibraryの分離

SnippetとLibraryは明確に区別する。

## Snippet

カーソル位置にコードを挿入するもの。

例：

```text
rep
for
binary search loop
BFS loop
coordinate compression
```

---

## Library

再利用可能なアルゴリズムやデータ構造。

例：

```text
DSU
Dijkstra
SegmentTree
LazySegmentTree
ModInt
Combination
RollingHash
```

Libraryはライブラリマネージャーで管理する。

# 9. ライブラリ検索

ライブラリ名だけでなく、Aliasやタグから検索できるようにする。

例えば、

```text

```

なら、

```text
Dijkstra<int>

Dijkstra + Path Restoration
```

を表示する。

また、

```text

```

や、

```text

```

などでも、

```text

```

を検索できるようにする。

# 10. ライブラリのメタデータ

各ライブラリにはコードだけでなく、メタデータを持たせる。

例：

```text

```

これにより検索性を高める。

---

# 11. ライブラリの依存関係

ライブラリ同士の依存関係を管理する。

例えば、

```text
Combination
└─ ModInt
```

という依存関係がある場合、

```cpp
#include <cp/math/combination.hpp>
```

だけを書けば、ModIntも自動的に読み込む。

同じライブラリが複数から要求されても、重複して導入しない。

---

# 12. ライブラリの利用方法

普段のコードでは、通常のC++に近い形を維持する。

例：

```cpp
#include <cp/dsu.hpp>
#include <cp/graph/dijkstra.hpp>

int main() {
    DSU dsu(N);

    ...
}
```

独自の、

```text
use dsu
```

のような構文は基本的には使わない。

理由は、

- C++として自然
- IDE補完が行いやすい
- 外部エディタでも理解できる
- コードの可搬性が高い

ため。

---

# 13. 提出時の自動展開

ライブラリシステムの中心となる機能。

開発時：

```cpp
#include <cp/dsu.hpp>
#include <cp/modint.hpp>
```

提出時：

```text
main.cpp

↓ Resolve libraries

DSU
ModInt

↓ Resolve dependencies

↓ Inline libraries

↓ Remove duplicate includes

↓ Generate

submission.cpp
```

最終的には、

```cpp
#include <bits/stdc++.h>
using namespace std;

// ===== DSU =====

struct DSU {
    ...
};

// ===== ModInt =====

struct ModInt {
    ...
};

int main() {
    ...
}
```

という単一ファイルを生成する。

---

# 14. 提出用コード生成

ユーザーは普段、

```cpp
#include <cp/...>
```

を使いながら開発する。

「Submit」時のみ、

> **ライブラリをすべて展開した1ファイルのC++コード**

を生成する。

この方式をライブラリシステムの基本方針とする。

例えばコードを選択して、

```text

```

登録画面：


競プロを続けるほど、

> **自分専用のライブラリ環境が育つ**

仕組みを目指す。

# 16. ライブラリのドキュメント

ライブラリ選択時にはAPIや計算量を表示する。

例：

```text

Usage

auto dist = dijkstra(g, start);

vector<long long>
```

# 17. ライブラリのバージョン管理

ライブラリ変更履歴をある程度保存する。

例：

```text

```

```text

```

新規問題作成時にテンプレートを選択可能にする。

例：

```text

Math
Heuristic

```

Minimal：


---

# 19. コンパイルエラー表示

C++の長いコンパイラ出力をそのまま表示するだけではなく、要点を先に表示する。

例：

```text
ERROR
line 53

sort(a);

a:
set<int>

sort requires:
RandomAccessIterator
```

その下に元のコンパイラ出力も表示する。

目的は、

> **競技中にエラーメッセージを読む時間を減らすこと**

である。

---

# 20. 競プロ向けLint

一般的なLintに加えて、競プロ特有のミスを検出する。

候補：

```text
Potential integer overflow

Possible int → long long

0-index / 1-index mismatch

vector size N
but accessing index N

INF + value may overflow

Recursive DFS may cause stack overflow

Uninitialized variable
```

完全な解析を目指すのではなく、

> **よくあるミスに気付くための補助**

として扱う。

---

# 21. 制約と計算量

問題文から、

```text
N ≤ 2 × 10^5
```

などを取得した場合、

```text
O(N)       OK
O(N log N) OK
O(N√N)     ?
O(N²)      NG
```

のような参考情報を表示する。

さらにコードから、

```cpp
for (...)
    for (...)
```

などを検出し、

```text
Potential O(N²)
```

と表示することも検討する。

---

# 22. Stress Test

Stress Testを標準機能として組み込む。

構成：

```text
Generator
gen.cpp

Brute Force
naive.cpp

Solution
main.cpp
```

実行すると、

```text
#1 OK
#2 OK
#3 OK

...

#184 FAILED
```

となり、

```text
Failing Input

7
4 2 1 5 3 7 6
```

を自動保存する。

可能であれば、

```text
Minimize Input
```

機能も追加する。

# 23. ヒューリスティックコンテストモード

通常問題とは別に、

```text
Normal
Heuristic
```

モードを用意する。

ヒューリスティックモードでは、複数ケースを実行してスコアを集計する。

例：

```text
Case      Score      Time

0000      812341     1.82 s
0001      731520     1.91 s
0002      923184     1.79 s
```

総合：

```text
Total Score

2,467,045
```

---

# 24. スコア比較

コード変更前後のスコアを比較する。

```text

```

ケースごとにも、

```text
0000  +3.1%
0001  -1.8%
0002  +8.7%
```

のように比較できるようにする。

# 27. 現時点での設計方針

現状、特に重要な方針は以下。

### エディタ

> コードを書くことより、競プロにおける試行錯誤を高速化する。

---

### ライブラリマネージャー

> 常時表示ではなく、必要に応じて別ウインドウとして起動する。

---

### ライブラリ利用

開発時：

```cpp
#include <cp/dsu.hpp>
```

提出時：

```cpp
// DSU implementation
struct DSU {
    ...
};
```

に自動展開する。

つまり、

> **開発中はモジュール化、提出時は単一ファイル化**

を基本思想とする。

---

# 28. このエディタの特徴

最終的には、

> **競プロ用IDE**

というより、

> **アルゴリズムを考え、実装し、実験し、検証するための専用環境**

を目指す。

特に、

- テストケース管理
- 軽量コード履歴
- Stress Test
- ライブラリ管理
- 提出時自動展開
- ヒューリスティックスコア分析

を統合することで、一般的なエディタとの差別化を図る。
